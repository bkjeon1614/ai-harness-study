# Feature Planning Workflow

> 새 기능을 설계 → 결정 → 분해하기까지의 표준 워크플로우. 이 문서는 **반드시 숙지하고 따라야** 한다.
> 산출물 3종: **PRD** (`prd.md`) → **이슈 목록** (`issues.md`) → (선택) **구현 계획**.

---

## 핵심 원칙

이 워크플로우 전체를 관통하는 3가지 원칙. 모든 결정 시 항상 이 원칙으로 검산한다.

1. **사용자 가치 우선** — 모든 산출물(스토리/이슈/AC)은 사용자가 직접 체감하는 행위/결과로 표현. 레이어 검증("타입 빌드 통과")은 산출물이 아닌 DoD.
2. **결정의 명문화** — 의미 있는 기술 선택은 **ADR**로 남긴다(Context/Decision/Alternatives/Consequences). "왜 안 했나"가 "왜 했나"만큼 중요.
3. **수직 슬라이싱** — 이슈는 데이터·API·UI를 가로지르며 **그 자체로 사용자에게 보이는 가치**를 제공. "데이터만", "API만" 같은 수평 슬라이스는 이슈가 아니다.

---

## 6단계 워크플로우

### 단계 1 — 요구 명확화 (Discovery)

**목적**: 무엇을 만들지 / 왜 만드는지 / 무엇은 만들지 **않는지**에 대한 합의.

**행동**:

- 한 줄 요약 도출: "사용자 X가 Y를 할 수 있게 한다."
- 비목표(Non-goals) 식별 — "이번엔 안 한다"를 명시.
- 성공 기준 협의 — 정성/정량 무관, 결정 가능한 수준이면 됨.
- 모호한 부분은 인터뷰형 질문으로 좁힌다. 가정으로 진행하지 않는다.

**산출물**: PRD §1 개요 (다음 단계에서 작성).

---

### 단계 2 — PRD 뼈대 작성

**목적**: 사용자 관점의 요구사항 + ADR 슬롯 + Out of Scope + 용어 정의를 문서화. **이 시점에 ADR 본문은 비워둔다.**

**파일**: `docs/features/<feature>/prd.md`

**필수 구조**:

```markdown
# <기능> PRD

## 1. 개요

- 1.1 한 줄 요약
- 1.2 배경 (왜 지금 만드나)
- 1.3 목표
- 1.4 비목표
- 1.5 성공 기준

## 2. 사용자 스토리

> US-N. <역할>로서 <목표>를 할 수 있어야 한다 — <이유>.
>
> 수용 기준 (AC): bullet 또는 G/W/T (이슈 단계에서 더 정교화)

## 3. 기술 결정 (ADR)

> 본문은 단계 3~4에서 채움. 이 시점엔 "결정해야 할 주제 N개"를 슬롯으로만 명시.

### ADR-N. <주제>

- Status: TBD
- Context: <!-- TBD -->
- Decision: <!-- TBD -->
- Alternatives:
  - (A) ...
  - (B) ...
- Consequences: <!-- TBD -->

## 4. Out of Scope

> 카테고리별 표로. 각 항목마다 "왜 미루는가" 명시.
> 카테고리 예: 활용 기능 / 1급 시민화 / 다중 사용자 / UX 보조 / 데이터 정책 / 비기능적 요구사항

## 5. 용어 정의

> 도메인 + 컴포넌트 + 패턴 용어 표.

## 6. 참고 문서

> 자매 spec, 디자인 시스템, 코드 컨벤션 등 상대 링크.
```

**가드레일**:

- 사용자 스토리는 **역할 + 목표 + 이유** 3요소 포함.
- Out of Scope는 PRD에서 가장 정성 들여 작성 — 스코프 누수를 막는 1차 방어선.
- ADR 슬롯은 **결정해야 할 주제**만 적고 본문은 비워둔다.

---

### 단계 3 — 기술 안 비교 (Architecture Alternatives)

**목적**: 채택할 단일 안을 정하기 전, **2~3개 안을 동일한 비교 기준**으로 분석. ADR을 채우는 근거가 된다.

**행동**:

- 가장 단순한 안(Minimal), 중간 안(Hybrid), 가장 야심찬 안(Big bet) 3개 정도 — 의미 있게 다르게 만들 것.
- **비교 기준은 미리 합의**. 도메인에 따라 다르지만 자주 쓰는 축:
  - 데이터 구조
  - API 레이어 변경지점
  - 상태관리 변경지점
  - 도메인 특화 동작(예: 저장 시점, 동기화 정책)
  - 컴포넌트/모듈 구조
  - 기존 패턴/컨벤션과의 일관성
  - 단위/통합/e2e 테스트 용이성
- 각 안에 대해 **모든 기준을 같은 형식**으로 채운다.
- 마지막에 **요약 비교표** + **추천 + 사유**.

**산출물**: 채팅/메모 또는 `docs/features/<feature>/alternatives.md` (선택).

**가드레일**:

- 추천은 사용자가 거부할 수 있는 형태로 제시 (3안 모두 살아 있는 비교).
- 사용자 선호(예: "커스텀훅 합성 선호")가 있으면 명시적으로 반영.

---

### 단계 4 — ADR 채움

**목적**: 채택안을 ADR 형식으로 명문화. 이후 합류하는 동료/Claude가 결정의 맥락을 재구성할 수 있게 한다.

**행동**: 단계 2의 ADR 슬롯을 다음 5필드로 채운다.

| 필드             | 내용                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------- |
| **Status**       | `Proposed` / `Accepted` / `Superseded`                                                    |
| **Context**      | 결정이 필요한 배경, 제약, 이해관계자. **사용자가 명시한 선호/사유**가 있다면 여기에 포함. |
| **Decision**     | 채택안 1~2문장 + 핵심 세부(시그니처, 파일 위치 등).                                       |
| **Alternatives** | 단계 3에서 비교한 안들 + 각각의 기각 사유. 채택안에 ← 표시.                               |
| **Consequences** | ✅ 긍정 결과 / ⚠️ 부정 결과·후속 작업. 미래의 변경 비용도 명시.                           |

**가드레일**:

- Decision만 있고 Alternatives가 없으면 ADR이 아니다 — 검토한 다른 안 + 기각 사유가 핵심.
- Consequences의 ⚠️는 의도적 트레이드오프를 명시 — 나중에 "왜 이런 결함이 있나" 질문 차단.
- **여러 ADR이 같은 철학을 공유**(예: "커스텀훅 활용")한다면 PRD §3 리드에 1줄로 요약해두면 좋다.

---

### 단계 5 — 수직 슬라이싱 이슈 분해

**목적**: PRD의 사용자 스토리·ADR을 **독립적으로 머지 가능한 슬라이스**로 쪼갠다. 각 슬라이스는 그 자체로 사용자에게 가치를 전달한다.

**파일**: `docs/features/<feature>/issues.md`

**필수 구조** (이슈마다 동일):

```markdown
## <ISSUE-ID> — <한 줄 제목 (사용자 행위/결과)>

### 설명

- 이 슬라이스가 무엇을 포함하는지 (데이터/UI/저장 흐름 등)
- **이번 슬라이스의 가치**: 사용자가 체감하는 변화 1~2문장 (PRD US-N 매핑)
- **스코프 안** / **스코프 밖** 명시

### 완료조건 (Acceptance Criteria)

#### <ISSUE-ID>.N — <시나리오 제목>

- **Given** <전제 상태>
- **When** <사용자 행동>
- **Then** <기대 결과>
```

**슬라이스 식별 가이드**:

1. 사용자 스토리(US)를 적기에 자르거나 묶는다 — 표시(read) → 추가(create) → 수정(update) → 삭제(delete)는 자연스러운 슬라이스 경계.
2. 첫 슬라이스는 **"보이게 만들기" tracer bullet**일 때가 많음 — 데이터 모델 + 시드 데이터 + 표시 UI를 한 슬라이스에 묶어 다음 슬라이스의 토대를 마련.
3. AC는 **사용자 가시 행위** 위주. "타입 빌드 통과" 같은 인프라 검사는 글로벌 DoD로 옮긴다.
4. **카디널리티 변형**(0개/1개/N개)을 AC로 분리해 회귀 위험을 잡는다.
5. **엣지케이스**(빈/공백/중복/특수문자 등)는 해당 행동 슬라이스의 AC 안에 포함 — 별도 "엣지케이스 이슈"를 만들지 않는다.

**Not Issued 섹션 필수**:
의도적으로 이슈에서 제외한 항목 표 — "수평 슬라이스라 제외" / "Out of Scope" / "추후 사용처가 생길 때 함께 도입" 같은 사유.

**의존성 / 진행 순서**: 이슈 그래프 간단 도식 + 머지 권장 순서.

---

### 단계 6 — 수평 슬라이싱 점검

**목적**: 단계 5에서 만든 이슈 목록에 **레이어 분리형(horizontal)** 누수가 없는지 검산.

**검토 체크리스트**:

- [ ] 단독 이슈 중 **사용자 가치가 0인 것**이 있는가? (예: "타입 추가만", "API helper만") → Not Issued로 옮기거나 다른 슬라이스에 합친다.
- [ ] AC 중 **사용자 행위가 아닌 검사**가 있는가? (예: `tsc 통과`, `seed JSON 필드 존재`) → 글로벌 DoD로 빼거나 사용자 행위로 재서술.
- [ ] **다른 이슈에 의존만 하고 가치를 추가 안 하는** 이슈가 있는가? → 의존 이슈에 합친다.
- [ ] **Not Issued 목록이 적절한가** — 추가해야 할 의도적 제외 항목이 있는가?

**처리**:

- 위반 발견 시 사용자에게 보고 + 2~3가지 정리안 제시 (재서술 / DoD 분리 / 다른 슬라이스에 흡수).
- 사용자가 "그대로" 선택해도 OK — 의식적 결정으로 남긴다.

---

## (선택) 단계 7 — 구현 계획

이슈 머지 직전, **bottom-up phase 분해**로 구현 순서를 잡으면 좋다. 의무는 아님.

권장 phase 순서:

1. 데이터/타입 토대
2. 순수 함수 (도메인 로직, 정규화/검증)
3. 커스텀훅 (또는 상태 관리 레이어)
4. dumb 컴포넌트 (props만 받는 view)
5. 컨테이너 + 기존 화면 통합
6. (선택) API helper/boundary 정비
7. 수동 e2e (사용자 스토리 골든 패스)
8. 정리 (lint, 다이어그램 재생성, 커밋 메시지)

각 phase는 다음 phase 시작 전 **검증 가능** (타입/단위/수동) 해야 한다.

## 안티패턴

다음은 워크플로우의 의도와 반대되므로 **하지 않는다**:

- ❌ ADR 본문을 PRD 뼈대 단계에서 미리 채우기 — 비교 단계 거치지 않은 결정은 약하다.
- ❌ 사용자 스토리 없이 바로 이슈 분해 — 사용자 가치 검증 누락.
- ❌ "데이터만 추가" / "API helper만" 단독 이슈 — 수직 슬라이싱 위반.
- ❌ AC에 `npm run build 통과` 같은 인프라 검사 — DoD로.
- ❌ Out of Scope를 빈 채로 두기 — 스코프 누수 방지선이 없어진다.
- ❌ 사용자 선호/제약을 ADR Context에 누락 — 미래에 결정 사유 재구성 불가.
- ❌ Alternatives 없는 ADR — 그냥 결정문이지 ADR이 아니다.
