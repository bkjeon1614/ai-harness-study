# 태그 기능 PRD (Product Requirements Document)

> 이 문서는 태그 기능의 **제품 관점** 요구사항을 정의한다. 구체적인 구현 결정과 엣지케이스 처리는 자매 문서 [`spec-fixed.md`](./spec-fixed.md)에 있다.
> 기술 결정(ADR) 섹션은 **다음 세션에서 논의/확정** 예정 — 현재는 골격만.

---

## 1. 개요

### 1.1 한 줄 요약

노트 앱 사용자가 각 노트에 **자유 입력 태그**를 붙여 분류할 수 있게 한다.

### 1.2 배경

현재 노트 앱은 제목과 본문만 저장한다. 노트 수가 늘어나면 사용자가 특정 주제/맥락의 노트를 다시 찾기 어렵다. 가장 가볍게 분류 신호를 도입하는 방법이 사용자가 직접 정의하는 **자유 입력 태그**다.

### 1.3 목표

- 사용자가 노트 작성/편집 흐름을 끊지 않고 태그를 추가·제거할 수 있다.
- 향후 검색/필터 기능을 붙일 수 있는 **데이터 토대**를 만든다 (이번 스코프는 데이터 + UI까지).
- 학습용 프로젝트의 코드 컨벤션(controlled 컴포넌트, props down + callback up, named export 등)을 깨지 않는다.

### 1.4 비목표 (이번 PRD에서 해결하지 않는 큰 줄기)

- 태그를 **이용한** 기능(검색·필터·추천 등) — 데이터만 마련, 활용은 별도 PRD.
- 태그 자체의 1급 자원화(색상·메타데이터·rename 등).
- 다중 사용자/공유 시나리오.

상세는 [§4 Out of Scope](#4-out-of-scope) 참조.

### 1.5 성공 기준

- 사용자가 노트 상세 화면에서 태그를 **3초 이내**에 추가할 수 있다 (입력 → Enter).
- 모든 노트가 `tags` 필드를 가지며, 빈 배열도 허용된다 (옵셔널 처리 코드 분산 금지).
- 기존 기능(노트 생성/수정/삭제/검색)이 회귀하지 않는다.

## 2. 사용자 스토리

### US-1. 태그 추가

> **노트를 작성하는 사용자**로서,
> 노트 편집 화면에서 **자유 텍스트로 태그를 추가**할 수 있어야 한다 —
> 나중에 같은 주제의 노트를 찾기 위해.

**수용 기준 (AC)**

- 노트 편집 화면 안에서 태그를 입력하는 영역이 보인다.
- 빈 값이나 공백만 입력하면 추가되지 않는다 (silent 무시).
- 이미 같은 태그가 있으면 중복 추가되지 않는다 (silent 무시, 입력만 비워짐).
- 다단어 태그(`front end`)도 그대로 허용된다.

### US-2. 태그 삭제

> **이미 태그를 붙인 사용자**로서,
> 추가된 태그를 **개별적으로 제거**할 수 있어야 한다 —
> 잘못 붙였거나 더는 관련 없을 때.

**수용 기준 (AC)**

- 추가된 각 태그 옆에 제거 액션이 보이거나 hover 시 노출된다.
- 제거 액션 1회로 해당 태그만 사라진다 (확인 모달 없음 — 분류 메타데이터는 가볍게 처리).

### US-3. 태그 확인

> **노트를 다시 여는 사용자**로서,
> 노트 상세 화면에서 **해당 노트의 태그 목록을 한눈에** 볼 수 있어야 한다 —
> 어떤 맥락의 노트인지 즉시 파악하기 위해.

**수용 기준 (AC)**

- 노트 상세(편집) 화면을 열면 저장된 태그가 표시된다.
- 태그가 없는 노트는 빈 영역만 보인다 (placeholder/안내 문구는 별도 합의).

### US-4. 태그 저장

> **노트를 편집하는 사용자**로서,
> 태그 변경이 노트의 다른 변경(제목/본문)과 **함께 저장**되어야 한다 —
> "저장" 한 번으로 모든 변경이 반영되는 일관된 경험을 위해.

**수용 기준 (AC)**

- 태그 추가/삭제는 서버에 즉시 반영되지 않는다.
- "저장" 버튼 클릭 시 제목·본문과 한 묶음으로 서버에 전송된다.
- 저장 전 화면을 떠나면 변경된 태그는 폐기된다 (제목/본문과 동일 정책).

## 3. 기술 결정 (ADR)

> ✅ 4개 ADR 모두 확정. 채택안은 **안 B (Hybrid + 커스텀훅 기반 합성)**.
> 채택 사유 요약: 사용자가 **커스텀훅 기반 합성 컴포넌트**를 선호하고 **리액트 순수 API**(`useState`, `useEffect`, custom hook)만으로 표현하기를 원함. 이후 다른 기능에서도 동일한 컴포지션 방향을 이어가기로 함. 단위 테스트는 훅 단독 테스트(`renderHook`) + 순수 함수 테스트 + 얇은 dumb 컴포넌트 렌더 테스트로 입자를 작게 가져간다.
> 자매 spec 문서: [`spec-fixed.md`](./spec-fixed.md) — Q1~Q4 결정과 본 ADR-001~004는 1:1 대응한다.

각 ADR 템플릿:

- **Status** — Proposed / Accepted / Superseded
- **Context** — 결정이 필요한 배경, 제약, 이해관계자
- **Decision** — 채택한 안, 한 문장 요약
- **Alternatives** — 검토한 다른 안과 기각 이유
- **Consequences** — 채택의 결과(긍정/부정), 따라오는 작업, 미래 변경 비용

---

### ADR-001. 태그 데이터 구조

**Status**: Accepted

**Context**:

- 노트는 강의/학습용 단일 사용자 앱으로, 현재 `db.json` 위 단일 리소스(`/notes`)만 운영 중.
- 태그는 노트를 분류하는 짧은 자유 입력 문자열이며, 자체 메타데이터(색상·설명·rename·통계 등)에 대한 요구가 현재 PRD 스코프에 없음 ([§4 Out of Scope](#4-out-of-scope)).
- `api/notes.ts`의 `Omit`/`Partial<Note>` 타입 좁힘 패턴, `NotesContext`의 mutation 1:1 매핑 컨벤션을 흔들지 않기로 한 컨벤션이 있다 (`CLAUDE.md`).
- 커스텀훅으로 데이터 변환·검증을 분리하려면, 데이터 모델 자체는 단순할수록 훅 조합이 깔끔해진다.

**Decision**:
`Note.tags: string[]` 인라인 배열로 저장한다. 별도 `/tags` 리소스는 만들지 않는다.

**Alternatives**:

- (A) **인라인 `Note.tags: string[]`** ← 채택. 변경 최소, 단일 리소스 패턴 유지, 훅 조합이 단순.
- (B) 별도 `/tags` 리소스 + `Note.tagIds: string[]` 참조 — rename/색상/전역 통계에 유리하지만, **현재 요구에 없는 기능을 위한 비용**이고 두 리소스 정합성을 클라이언트가 책임져야 함. NotesContext 단일 패턴도 일반화 필요 → 오버엔지니어링.
- (C) `/note-tags` join 리소스 — N:M 관계가 의미 있을 때만 유효. 평면 자유 입력에서는 불필요.

**Consequences**:

- ✅ `api/notes.ts` 시그니처 변경 없음. `createNote`/`updateNote`가 자동 흡수.
- ✅ `NotesContext` 변경 없음. `useNotes()`가 그대로 `Note.tags`를 노출.
- ✅ 데이터가 `string[]`이라 정규화/판정 로직을 순수 함수로 표현 가능 → 커스텀훅이 그 위에 얇게 얹힘.
- ⚠️ `db.json` 시드의 기존 노트에 `tags: []` 1회 백필 필요 (옵셔널 처리 코드 분산 방지).
- ⚠️ 1급 시민 기능(rename·색상·전역 통계)이 필요해지면 별도 리소스로 마이그레이션 — 그 시점에 별도 ADR로 다룸.
- ⚠️ 같은 태그명이 노트마다 중복 저장됨(전역 인덱스 없음). 현재 규모에선 무시.

### ADR-002. 태그 입력 UI 패턴 (컴포넌트 + 커스텀훅 합성)

**Status**: Accepted

**Context**:

- 사용자는 **커스텀훅 기반 합성 컴포넌트**를 명시적으로 선호. 이후 다른 기능에서도 동일 방식 유지 예정.
- 리액트의 순수 API(`useState`, `useEffect`, `useCallback`, custom hook)만으로 표현 — 외부 폼/태그 라이브러리 미도입.
- 단위 테스트 용이성: 로직을 훅으로 추출하면 `@testing-library/react`의 `renderHook`으로 **컴포넌트 렌더 없이** 훅 단독 테스트 가능. dumb 컴포넌트는 props 입출력만 검증.
- spec-fixed.md Q2: Chip + Enter 확정 + hover 시 `×` 노출, 다단어 태그 허용 (스페이스/콤마는 확정 트리거 아님).

**Decision**:
컴포넌트는 **3분할 합성**으로 두고, 입력 상태/검증/추가/제거 같은 **모든 로직은 커스텀훅(`useTagInput`)으로 추출**한다. 컴포넌트는 훅이 반환한 값/핸들러를 렌더에 꽂는 얇은 view 역할만.

| 구성요소               | 역할                                                                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `TagField` (container) | `NoteEditor` 안에서 호스팅. `value: string[]` + `onChange`만 받는 controlled 컴포넌트. 내부에서 `useTagInput` 호출 + chip 목록 + input 배치. |
| `TagInput` (dumb)      | 텍스트 input 1개. props: `{value, onChange, onSubmit}`. Enter 키 감지 후 `onSubmit` 호출.                                                    |
| `TagChip` (dumb)       | 개별 chip + 삭제 버튼. props: `{label, onRemove}`. hover 시 `×` 노출은 CSS(`group-hover`)로.                                                 |
| `useTagInput` (hook)   | 추가/삭제/입력 상태 관리, 정규화·중복 판정(ADR-004 순수 함수 호출). 반환: `{inputValue, setInputValue, addTag, removeTag, tags}`.            |

**Alternatives**:

- (A) **3분할 컴포넌트 + 커스텀훅 추출** ← 채택. 단위 테스트 입자 작고, 훅 재사용 여지(다른 화면의 TagField 등), 사용자 선호 패턴.
- (B) 단일 `TagInput` 컴포넌트에 모든 책임 — 빠르지만 한 파일에 케이스가 몰려 테스트 비대화. 향후 변형이 늘어나면 분해 비용.
- (C) 외부 폼 라이브러리(`react-hook-form`, `react-tag-input`) — 의존성/학습 비용, 컨벤션(controlled + 순수 API) 위반.
- (D) `useReducer`로 입력 상태 관리 — 액션 종류가 적어 오버킬. `useState` + 핸들러로 충분.

**Consequences**:

- ✅ 입력 룰(trim, dedup, Enter)이 훅 안에 모이고 컴포넌트 밖에서 단위 테스트 가능 — `renderHook` 호출 → 결과 검증.
- ✅ `TagInput`, `TagChip`은 props만 받는 dumb 컴포넌트 → 렌더 테스트가 단순(스냅샷/이벤트 검증).
- ✅ **커스텀훅 합성 패턴이 코드베이스에 자리 잡음** → 다음 기능(검색 필터, 폼 검증 등)도 동일 방향으로 확장.
- ⚠️ 파일 수 증가: `TagField.tsx`, `TagInput.tsx`, `TagChip.tsx`, `useTagInput.ts` (+ 각 테스트). 학습용 프로젝트에서 수용 가능.
- ⚠️ 훅이 너무 잘게 쪼개지면 응집도 저하 — "태그 입력 흐름" 한 책임 단위로 한 훅에 묶는 규율 필요.
- ⚠️ 디자인 시스템의 [Knowledge Token](../../design-system/components/knowledge-token.md) 사양과 일치시켜야 함 — chip 스타일은 그 문서 기준.

### ADR-003. 서버 반영 시점

**Status**: Accepted

**Context**:

- 현재 `NotesContext`의 mutation 패턴: **서버 응답을 받은 뒤 로컬 state 갱신** (낙관적 업데이트 아님, `CLAUDE.md` 명시).
- 노트 편집 UX는 "제목·본문 변경 후 저장 버튼" 멘탈 모델 — 태그만 즉시 PATCH가 가면 모델이 분기.
- spec-fixed.md Q3: bulk save.
- 단, 향후 "즉시 저장 모드" 같은 옵션을 데이터 모델 변경 없이 열어두면 ADR-001과 시너지.
- 커스텀훅 관점: 서버 호출 boundary를 helper로 분리해두면 미래에 `useTagMutations(noteId)` 같은 훅으로 한 번 더 감쌀 수 있음 → 모킹/테스트 단순화.

**Decision**:
태그 변경은 **저장 버튼 클릭 시** 제목·본문과 함께 일괄 PATCH/POST 한다. 단, `api/notes.ts`에 `updateNoteTags(id, tags: string[])` 얇은 helper를 미리 노출해, 향후 즉시 저장 UX가 필요해지면 데이터 모델 변경 없이 전환 가능하도록 한다.

**세부**:

- `api/notes.ts`: `updateNoteTags(id, tags)`는 내부적으로 `updateNote(id, { tags })`를 호출하는 thin wrapper. mutation 동사 `update` 컨벤션 유지.
- `NotesContext`도 동일 이름(`updateNoteTags`)을 1:1로 노출 (`api` ↔ `Context` 함수명 매핑 컨벤션 유지).
- `NoteEditor.handleSave`는 기존처럼 `createNote`/`updateNote` 한 호출로 묶어 보냄 — `updateNoteTags`는 호출하지 **않음** (현재는 helper만 존재, 사용처는 미래).

**Alternatives**:

- (A) **저장 시 bulk PATCH + helper만 미리 마련** ← 채택. 현재 UX 일관성 + 미래 확장 진입점.
- (B) 태그 추가/삭제 즉시 `PATCH /notes/:id` — 사용자 피드백 즉각적이지만, 저장 버튼 모델과 충돌. 실패 회복(rollback) 책임 추가.
- (C) 낙관적 업데이트 + 백그라운드 sync — 학습용 범위에서 비용 효익 부적합. 기존 컨벤션(서버 응답 후 갱신)을 깬다.
- (D) helper도 추가하지 않고 100% bulk만 — 가장 단순하지만, 미래 즉시 저장 도입 시 데이터 모델은 그대로 두더라도 API 표면을 새로 뚫어야 함.

**Consequences**:

- ✅ 기존 mutation 패턴/저장 UX 그대로 유지 — 회귀 위험 낮음.
- ✅ `updateNoteTags` helper가 미래 즉시 저장 도입의 진입점이 됨, 그 위에 `useTagMutations(noteId)` 같은 커스텀훅 얹기 자연스러움.
- ✅ 단위 테스트: helper는 순수하게 `updateNote` 호출만 검증, 향후 훅 단위 테스트는 helper만 모킹하면 충분.
- ⚠️ 현재 사용처가 없는 helper가 코드에 들어감 — "지금 쓰지 않는 API" 컨벤션과 약한 마찰. 함수 위 주석으로 "future: 즉시 저장 모드 진입점" 명시.
- ⚠️ 저장 전 화면을 떠나면 태그 변경 폐기 — 제목/본문과 동일 정책. 사용자 별도 안내 없음.

### ADR-004. 중복 판정 정책

**Status**: Accepted

**Context**:

- 사용자는 "JavaScript", "javascript", " JavaScript "을 같은 태그로 인식할 가능성이 큼.
- 저장값을 lowercase로 강제하면 사용자가 입력한 원본 케이스가 사라짐.
- 다단어 태그(`front end`)는 허용 — 중간 공백은 정규화하지 않음.
- `alert()` 금지 룰(`CLAUDE.md` 에러 처리)과 결합 — 중복 시 사용자 알림 없음(silent).
- 커스텀훅 관점: 정규화/판정 로직은 **순수 함수**로 추출하면 단위 테스트가 가장 단순 (입력 → 출력 표 검증). 훅은 이 순수 함수를 조합만 한다.

**Decision**:
대소문자 무시 + 양끝 trim 기준으로 중복 판정한다. 저장 값은 **입력 원본 그대로**(케이스 보존, 양끝 trim만 적용). 중복/빈값은 silent 무시(input만 비움).

**세부 (순수 함수 시그니처)**:

```ts
// src/lib/tag.ts (또는 useTagInput.ts 내부 export)
export function normalizeForCompare(input: string): string {
  return input.trim().toLowerCase();
}

export function sanitizeForStore(input: string): string {
  return input.trim(); // case 보존, 중간 공백 보존
}

export function isDuplicate(input: string, existing: string[]): boolean {
  const key = normalizeForCompare(input);
  return existing.some((t) => normalizeForCompare(t) === key);
}
```

이 셋은 **컴포넌트/훅과 분리된 순수 모듈**로 두고, `useTagInput`이 호출한다.

**Alternatives**:

- (A) **대소문자 무시 + 양끝 trim, 저장은 원본 (case 보존)** ← 채택. 사용자 의도 보존 + 시각적 중복 방지.
- (B) 대소문자 무시 + 양끝 trim, **저장은 lowercase 강제** — 일관성은 ↑이지만 사용자 입력 케이스 손실. 향후 전역 검색 시에나 유리 — 현재 스코프 아님.
- (C) case-sensitive 완전 동일 비교 — "JavaScript"와 "javascript"가 공존, 시각적 혼란.
- (D) Unicode NFC 정규화 + 중간 공백 압축까지 — 다단어 태그 의도 손상, 과도한 정규화.

**Consequences**:

- ✅ 순수 함수라 단위 테스트가 가장 단순 — 입력/출력 표만 작성, 컴포넌트 렌더 없음.
- ✅ 커스텀훅(`useTagInput`)은 이 함수들을 조합만 함 → 책임 분리 명확.
- ✅ 정책이 한 곳에 모임 → 변경(예: NFC 정규화 추가) 시 한 파일만 수정.
- ⚠️ 사용자가 중복 시 피드백 못 받음(silent). UX 불만 누적 시 별도 ADR로 안내 정책 재검토.
- ⚠️ "JavaScript"와 "javascript"가 다른 노트에 따로 저장될 수 있음 — 같은 노트 안에서만 중복 방지. 전역 정규화는 ADR-001 (B) 마이그레이션 시 함께 결정.

## 4. Out of Scope

이번 PRD는 **태그 데이터의 생성/저장/조회 UI**까지만 다룬다. 아래 항목들은 모두 명시적으로 범위 밖이며, 별도 PRD/spec에서 다룬다.

### 4.1 태그 활용 기능 (별도 PRD)

| 항목                                           | 왜 미루는가                                                                                                                |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **태그 기반 검색/필터**                        | 현재 `SearchBar`는 제목 검색 전용. 태그 검색은 UX(다중 선택? AND/OR? 자동완성?)와 데이터 인덱싱 결정이 필요해 별도 사이즈. |
| **사이드바 `NoteList` 항목에서 태그 미리보기** | 시각 노이즈 우려, 컴포넌트 폭 제약. 디자인 시스템에서 별도 검토 후 결정.                                                   |
| **태그 자동완성**                              | 기존 태그 인덱싱이 필요 — 데이터 구조 결정(ADR-001)에 의존.                                                                |
| **태그 사용 빈도/통계 대시보드**               | 분석 자체가 별도 가치 명제.                                                                                                |
| **추천 태그 / 자동 태깅**                      | ML/NLP 영역. 학습용 프로젝트 범위 밖.                                                                                      |

### 4.2 태그 자체의 1급 시민화

| 항목                                        | 이유                                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| **태그 색상**                               | 데이터 구조가 `string[]`이면 불가. (B) 리소스 마이그레이션 후 별도 PRD. |
| **태그 설명/메타데이터**                    | 동상.                                                                   |
| **태그 rename** (전역 일괄)                 | 단순 인라인 배열에선 모든 노트 순회 필요. 1급 시민화 후.                |
| **태그 merge** (둘을 하나로)                | 동상.                                                                   |
| **태그 archive / soft delete**              | 별도 리소스가 있어야 의미.                                              |
| **태그 계층/카테고리** (#frontend > #react) | 본 PRD의 "자유 입력 평면 태그" 컨셉과 충돌.                             |
| **태그 별 권한/공개 범위**                  | 다중 사용자가 전제.                                                     |

### 4.3 다중 사용자/협업

| 항목                         | 이유                 |
| ---------------------------- | -------------------- |
| **태그 동시 편집 충돌 해소** | 현재 앱은 싱글 유저. |
| **사용자별 태그 가시성**     | 동상.                |
| **태그 공유 / import**       | 동상.                |

### 4.4 UX 보조 기능

| 항목                                                  | 이유                                                                            |
| ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| **사용자 알림 toast/modal**                           | 코드베이스 룰: `alert()` 금지, 에러는 `console.error`만 (CLAUDE.md §에러 처리). |
| **태그 수/길이 하드 제한 표시**                       | 입력 자체에 하드 제한을 두지 않기로 했으므로(spec-fixed.md), 안내 UI도 없음.    |
| **키보드 단축키** (예: `Ctrl+K`로 태그 입력 포커스)   | 학습용 범위에서 우선순위 낮음.                                                  |
| **드래그로 태그 순서 변경**                           | 태그 순서는 **입력 순**으로 고정. 순서가 의미 없음.                             |
| **태그 import/export** (CSV·JSON 일괄)                | 별도 도구 영역.                                                                 |
| **모바일/터치 최적화 UI**                             | 현재 데스크톱 기준. 별도 반응형 작업.                                           |
| **접근성(a11y) 세부 인증** (ARIA, 스크린리더 라벨 등) | 기본 시맨틱은 지키되, WCAG 레벨 인증은 별도.                                    |
| **다국어 i18n 처리**                                  | 태그는 입력 그대로 저장(언어 무관). UI 문자열의 i18n은 앱 전체 별도 작업.       |

### 4.5 데이터 정책

| 항목                                               | 이유                                                                  |
| -------------------------------------------------- | --------------------------------------------------------------------- |
| **태그 유효성 sanitize** (XSS 방어, 특수문자 필터) | 학습용 + json-server 환경. 표시 시 React가 기본 escape.               |
| **태그 데이터 마이그레이션 도구**                  | 1회성 backfill만 필요(`db.json` 직접 수정). 운영성 마이그레이션 없음. |
| **태그 인덱스 / 캐시 / 성능 최적화**               | 노트 수가 학습용 수준. 대량(N>1000) 시나리오 미고려.                  |
| **태그 변경 이력(audit log)**                      | 별도 가치 명제.                                                       |

### 4.6 비기능적 요구사항(이번엔 약식)

| 항목          | 이번 처리                                                           |
| ------------- | ------------------------------------------------------------------- |
| **성능**      | 노트 100개 × 태그 평균 5개 수준에서 체감 지연 없음. 정량 목표 없음. |
| **보안**      | 싱글 유저 + 로컬 json-server. 보안 모델 없음.                       |
| **백업/복구** | `db.json` 파일 그 자체가 저장소. 별도 백업 없음.                    |

## 5. 용어 정의

| 용어                                   | 정의                                                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **노트(Note)**                         | 제목·본문·생성/수정 타임스탬프를 가진 사용자 작성 단위. 본 PRD 이후 `tags` 필드 추가. 정의는 `src/types/note.ts`.                                 |
| **태그(Tag)**                          | 노트 분류용 짧은 문자열. 사용자가 자유 입력하며, 별도 리소스가 아닌 노트의 속성으로 인라인 저장(ADR-001에서 재검토).                              |
| **태그 토큰 / 칩(Chip)**               | 추가된 태그를 시각적으로 표현하는 알약 모양 UI 요소. 디자인 시스템의 [Knowledge Token](../../design-system/components/knowledge-token.md)에 대응. |
| **`NoteEditor`**                       | 노트 작성/편집 화면 컴포넌트. 태그 UI는 이 컴포넌트 내부에만 등장.                                                                                |
| **`NoteList`**                         | 사이드바의 노트 목록 컴포넌트. 본 PRD 스코프에서는 태그를 표시하지 않음.                                                                          |
| **`TagInput`**                         | 태그 추가/표시/삭제를 담당할 신규 컴포넌트(예정). 자세한 시그니처는 [`spec-fixed.md`](./spec-fixed.md).                                           |
| **Controlled 컴포넌트**                | React 패턴 — 부모가 state를 보유하고 자식은 `value` + `onChange`로만 상호작용. 본 프로젝트 컨벤션.                                                |
| **정규화(Normalization)**              | 비교 또는 저장 전에 문자열을 표준 형태로 변환하는 행위 (예: lowercase, NFC, trim). 적용 범위는 ADR-004에서 결정.                                  |
| **Trim**                               | 문자열 양끝 공백 제거. 본 PRD에서는 태그 입력에 기본 적용.                                                                                        |
| **중복 판정(Dedup)**                   | 새로 입력된 태그가 이미 존재하는지 판정하는 기준. 대소문자/공백/유니코드 정규화 범위는 ADR-004.                                                   |
| **Silent 무시**                        | 사용자에게 별도 피드백(alert/toast 등) 없이 입력만 비우는 처리. 본 프로젝트의 `alert()` 금지 룰과 결합.                                           |
| **낙관적 업데이트(Optimistic Update)** | 서버 응답 전에 로컬 state를 먼저 갱신하는 패턴. 현재 코드 컨벤션은 **낙관적 업데이트 아님** (서버 응답 후 갱신). ADR-003에서 재검토.              |
| **백필(Backfill)**                     | 기존 데이터에 신규 필드를 채워 넣는 일회성 마이그레이션. `db.json`의 기존 노트에 `tags: []`를 추가하는 작업.                                      |
| **ADR (Architecture Decision Record)** | 의미 있는 기술 결정의 배경/대안/결과를 짧게 기록하는 문서 형식. 본 PRD §3의 단위.                                                                 |
